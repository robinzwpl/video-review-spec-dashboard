### 抖音链接抓取失败的记录（重要前置结论）

原始链接 `douyin.com/user/self?...modal_id=7688759527650381107` **无法抓取**：

- 用户「另存为网页」得到的 `.htm`（848KB）里 `RENDER_DATA` 解开后只有页面框架配置，
  `video_id` / `play_addr` / `aweme_detail` 命中数全为 **0**
- `iesdouyin` iteminfo 返回空响应体；两个 detail 接口均 **403**
- 根因：详情数据靠 `a_bogus` + `msToken` + 登录 Cookie 走 XHR 拉取，「另存为网页」存不到

**结论**：本 skill 的输入是**本地视频文件**，不负责下载。下载请用 Douzy（见 `SKILL.md` 第 1 节）。

## 四、十一个坑

按发现顺序排列，每个给「现象 / 根因 / 解法 / 代价」。

### 1. RapidOCR 不接受 PIL Image 对象 ★ 最隐蔽

- **现象**：`output/logs/pipeline.log` 里白纸黑字写着
  「OCR 完成: 226 帧，**0 帧有文字，共 0 个文本框**，耗时 16s」
- **根因**：RapidOCR 只接受 路径 / numpy / bytes。传 PIL Image 抛 `LoadImageError`，
  而这个异常被 `try/except` **吞掉了**，表现成"每帧都识别成功、只是没文字"
- **解法**：`engine(np.array(img))`
- **代价**：差点让整套流程的结论变成"这个视频 OCR 不出来"
- **附带**：同版本 `score` 返回**字符串**，需 `float(score)` 不能 `round(score)`

### 2. 刷新率取值按 x 排序 → 5 台机型全错 ★ 造成过实际错误

- **现象**：创维 A4F Pro 的原生刷新率被记成 144Hz（实为 60Hz）
- **根因**：实测「原生刷新」标签 y=587，同行值「4K 60Hz」y=572（差 15），
  下一行补充说明「144Hz高刷·HDMI1080P输入」y=607（差 20）。
  按 x 坐标取最近值会误取**下一行**的补充说明
- **解法**：先按 `|Δy|` 取最近行，同行内再按 x 拼接（铁律 M4）
- **修正结果**：创维A4F Pro 144→60、A6F Ultra 300→144、大玩家G7 330→180、A7H 165→60

### 3. 底部栏位置误判 200px

- **现象**：内存覆盖率只有 2/32
- **根因**：预估底部横排栏在 y 730-800，**实测在 y 920-1005**
- **解法**：按实测坐标重切
- **代价**：白跑一轮 OCR

### 4. 开篇总览页必然错配

- **现象**：15.8-18.3s 是「32款一起拆开看」总览页，多机型卡片同屏
  （16.3s 一帧内同时含 海信E3Q / 雷鸟鹏7Plus / 100%sRGB / 100%BT.709 / 2GB/64GB / 2GB/32GB）
- **解法**：`exclude_before_sec: 120`，`first_seen < 120s` 的帧一律不参与参数解析（**排除 86 帧**），
  仅用于章节定位
- **注意**：这类帧留着做章节定位是有价值的，只是不能参与参数解析

### 5. 型号被识别成 "P3"

- **现象**：华为 Vision智慧屏6 的 model 变成 `P3`
- **根因**：`98% DCI-P3` 里的 "P3" 被型号正则捕获
- **解法**：加 `model_negative` 负向词表，命中色域标准词的候选丢弃

### 6. 色域标注技术上不成立

- **现象**：TCL V8M 画面标注 `130% BT.709`、创维A8H 标注 `110% DCI-P3`
  （覆盖率不可能超过 100%）
- **核实**：画面原图如此，**OCR 无误**
- **处理**：据实记录 + 标「待核对」，**不擅自改写成 100%**
- **理由**：擅自改写会掩盖"这个视频的标注本身有问题"这个事实

### 7. 后台进程被回收 → 交付事故

- **现象**：首轮交付时看板没展示给用户，系统回退打开了核对表，用户反馈"看板里没有这个功能"
- **根因**：`nohup ... &` 启动的 http.server 随 shell 退出被回收，
  `present_files` 探测到 8899 端口不可达后回退到目录内第一个 HTML
- **解法**：本地预览服务必须 `run_in_background=true` 启动，且首项就传看板 URL

### 8. jsdelivr CDN 不可达 → 图表全白

- **现象**：看板图表区空白，**没有任何报错**
- **根因**：`cdn.jsdelivr.net` 在本机不通（curl 返回 000），而 `unpkg.com` 正常
- **解法**：把 `echarts.min.js`（1MB）内嵌进 HTML，生成零外部依赖单文件
- **这已是铁律 M11**：网络不可控，单文件看板必须自包含

### 9. av / faster-whisper 版本冲突

- **现象**：`TypeError`
- **根因**：faster-whisper 1.2.1 调 `av.open(..., metadata_errors="ignore")`，
  而 av 19.0 已移除该参数；av 14.x 在 Python 3.13 无预编译 wheel
- **解法**：本地已有 16kHz WAV，用 `wave` 读成 float32 numpy 数组直接喂 `model.transcribe(array)`，
  绕过 `decode_audio`

### 10. turbojpeg 新版 API 三处变更

- 导入名是 `from turbojpeg import compress`（**不是** `TurboJPEG`）
- 枚举名是 `SAMP.Y420`（**不是** `YUV420`）
- 参数名是 `pixelformat`（**不是** `pixel_format`），且 `subsamp` 必传

### 11. 底部栏等分无效

- **现象**：内存覆盖 2/32、处理器 2/32
- **根因**：字幕居中约 x 600-1340，**压在底部栏上**；四等分切会把字幕一起切进来
- **解法**：按实测 x 边界分四段并跳过字幕区
  - x150-560 → 内存/存储（干净）
  - x620-900 → HDMI（常被字幕压住）
  - x960-1180 → 发声单元（常被字幕压住）
  - x1340-1800 → 处理器（干净）
- **效果**：内存 2/32 → **31/32**，处理器 2/32 → **29/32**
- **教训**：**必须按实测 x 边界切，等分无效**（这条后来写成了 `04_ocr.py` 的注释，
  早期版本里那个"四等分"的死函数主张的做法正好相反，已在改造时删除）

## 五、画面版式的实证发现

| 项 | 实测值 |
|---|---|
| 布局 | 全屏参数卡，**双列**：标签列 x≈480-1000，值列 x≈1060-1400 |
| 主区（竖排） | y 240-860：屏幕 / 分区 / 亮度 / 刷新 / 色域 |
| 底部横排栏 | **y 920-1005**（标签行 y≈920-945，数值行 y≈960-1005） |
| 口播字幕 | 底部居中 x 600-1340，白字黑描边，识别率高，但**压住底部栏** |
| 参数文字 | 压在花哨背景上（金色羽饰等），对比度低 → 需分区域裁切 + 对比度增强 |
| 过场动画帧 | 画面模糊只有字幕，价值低 |
| 博主句式 | 「第二台，红米A75」——「第N台 + 型号」是章节定位的抓手 |

数值会被 OCR 粘连成整行（实测 `2GB/64GBEA00aHSnoA55`），所以底部栏必须分段识别。

## 六、人工核对闭环

1. **出图**：`07_contact_sheet.py` 按品牌分批、每批 6 台、左参数卡图右提取结果
   → 实际产出 **10 批**（`contact_sheet_1_创维.jpg` … `contact_sheet_10_小米.jpg`）
2. **核对**：用户逐批看图核对
3. **回填**：确认值写进 preset 的 `overrides`——**2 台机型 11 个字段**
   - 创维A4F Pro：色域 100.0% sRGB、内存 2GB、存储 64GB、处理器 四核A55、HDMI2.1 2个、发声单元 2个
   - 华为Vision智慧屏6：屏幕 VA软屏、内存 8GB、存储 64GB、处理器 四核A73、刷新率_倍频 288Hz
4. **标记来源**：回填值带 `source="用户截图确认"` / `verified_by="user_screenshot"`，
   核对表里汇总为「人工确认」，看板上打「已核对」标签
5. **重跑下游**：回填后重跑 08/09，看板与核对表同步更新

> 这一步不能省。OCR 再准也会有口径误判（如原生 vs 倍频刷新率），
> 只有人看着画面才能判断"这个数字说的是不是这件事"。

## 七、口径陷阱实录

画面上明确标注、必须记录下来的口径差异：

- `客服:原生4K60Hz；144Hz限1080P输入` → 高刷值**仅在 1080P 下生效**
- `客服:原生4K144Hz；300Hz为2K模式` → 300Hz 实为 2K 模式
- `2K高刷模式330Hz` → 同上，原生 180Hz
- `高刷2K 165Hz · PC端720P 300Hz`
- `(宣称)` 标记 → 厂商宣称值非实测（如 vidda 大玩家G7 的 7300nit）
- `参考价为国补后价格，需符合地区补贴条件` → 价格含补贴口径
- 亮度常为**区间**：`400-600 nits` / `1500-2000 nits` / `4000-5000 nits`
- 分区可为**档次**：`100-200级`（非精确值）
- 海信用「**玲珑控色区**」替代「背光分区」（小墨E5S Pro 2640 个、E8S 4200 个），
  与背光分区算法不同，**不可混算**，看板单列一栏

## 十、如果重来一次会怎么做

1. **先冻结回归基线再动手** —— 这次是改造前才补的基线。有了基线才敢大改。
2. **先跑 `05_discover.py` 探版式**，别靠肉眼预估坐标（坑 3 就是这么踩的，白跑一轮 OCR）。
3. **开篇总览页一开始就排除**（`exclude_before_sec`），不要等发现错配再回头。
4. **人工核对前移** —— contact sheet 应该在第一次出参数时就生成，而不是等到最后。
5. **底部栏按实测 x 边界切**，不要等分（坑 11，覆盖率差 15 倍）。
6. **预览服务用 `run_in_background=true`**，且交付首项就传看板（坑 7）。
7. **图表资源一律内嵌**，不依赖 CDN（坑 8）。
